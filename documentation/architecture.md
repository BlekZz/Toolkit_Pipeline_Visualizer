# Architecture

> Status: V1 complete — reflects actual implementation as of 2026-06-26.

## Product Overview

Pipeline Schedule Visualizer is a **local-first, read-only calendar dashboard** for data pipeline schedules.

Users import a JSON file describing their projects, pipelines, and schedules. The app validates the JSON, expands recurrence rules within the visible calendar range, and renders occurrences on a calendar. Users can filter, inspect, and navigate schedules without any backend, authentication, or data leaving their machine.

**Key assumption:** users maintain the JSON file externally (in a git repo, shared drive, or generated by an AI). V1 does not sync with orchestrators (Airflow, Dagster, Prefect) or write back to any source.

## Tech Stack

| Layer | Choice |
|---|---|
| UI framework | React 19 + TypeScript 6 |
| Build tool | Vite |
| Calendar rendering | FullCalendar Community (daygrid + timegrid + interaction plugins) |
| Recurrence — RRULE | rrule |
| Recurrence — Cron | cron-parser |
| Schema validation | Zod (discriminatedUnion on `recurrence.mode`) |
| State management | useState + useReducer (no external library) |
| Runtime | Browser-only; no server, no database, no network calls |

## Entity Model

```
Project --pipelineRefs[]→ Pipeline --schedules[]→ Schedule
```

- **Project** — business-intent view. References pipelines by id. Never embeds pipeline objects.
- **Pipeline** — reusable data-operation unit. Can appear in multiple projects. Canonical owner of schedules.
- **Schedule** — formal execution definition. Must nest inside a pipeline. `job` is a UI/AI alias only.

`pipeline.projectRefs` is derived at runtime by inverting `project.pipelineRefs` — it is never in source JSON.

## Data Flow

```
User imports JSON file
        │
        ▼
Zod validates ScheduleDocument
        │ invalid → show errors, keep previous data
        ▼
normalizeScheduleDocument(doc, viewContext)
  1. Apply timezone defaults (cascade: project → pipeline → schedule)
  2. Derive pipeline.projectRefs (invert project.pipelineRefs)
  3. Inject RRULE DTSTART from startDate + time + schedule.timezone
  4. Compute tag inheritance (schedule direct > pipeline inherited; project additive)
        │
        ▼
expandRecurrence(occurrences, visibleRange)
  — expands only within current calendar view range
  — deduplicates: one CalendarOccurrence per (pipelineId, scheduleId, scheduledStart)
  — attaches projectContexts[] to each occurrence
        │
        ▼
FullCalendar renders CalendarOccurrence[]
  — filter state applied before render
  — click → detail panel
```

Source JSON is **never mutated** during normalization or expansion.

## Occurrence ID Format

`pipelineId::scheduleId::scheduledStart`

`scheduledStart` is UTC ISO 8601 with Z suffix (e.g. `sales-mart::weekly-sales-refresh::2026-07-07T01:00:00Z`).

## Timezone Strategy

- Default timezone: `Asia/Taipei`
- Pipeline timezone **must equal** all child schedule timezones (Zod validation error if mismatched)
- Project ↔ pipeline timezone mismatch: **allowed** — display layer converts transparently
- DST: UTC instant preserved (absolute). Occurrences in the DST missing hour are silently dropped.
- Display timezone depends on view context:

| View context | Display timezone |
|---|---|
| Single project view | `project.timezone` |
| Single pipeline view | `pipeline.timezone` |
| Global view | Browser `Intl.DateTimeFormat().resolvedOptions().timeZone` |

## Recurrence Modes

Three mutually exclusive modes per schedule (discriminated on `recurrence.mode`):

| Mode | Field | Example |
|---|---|---|
| `simple` | `frequency`, `interval`, `byWeekday`, `byMonthDay`, `endDate` | weekly every Monday |
| `rrule` | `rrule` string (DTSTART injected by normalization) | `FREQ=WEEKLY;BYDAY=MO` |
| `cron` | `cron` expression (interpreted in `schedule.timezone`) | `0 9 * * 1` |

Plus `type: "one_time"` with `startDateTime`.

Recurrence expansion happens **only within the visible view range** — infinite occurrences are never pre-generated.

## Trust Boundaries

V1 has exactly one trust boundary: the user's local file system → the browser.

- No server. No API calls. No data leaves the user's machine.
- No authentication. Single implicit user.
- The browser's native file picker controls file system access.
- No secrets. No environment variables. No `.env` file.
